# Security & Privacy Architecture — Savanna Career Gateway

## 1. Threat Model & Safeguarding Philosophy

The platform serves vulnerable jobseekers and learners who may experience displacement, economic precarity, or disability. In this context, data confidentiality and autonomy are vital safeguards.

### Core Safeguarding Principles:
1. **Never Force Diagnosis Disclosure**: A candidate should never be required to disclose a medical condition, diagnosis code (e.g. ICD-10), or produce physician notes to receive workplace accommodations.
2. **Alternative Identity Pathways**: Learners who lack national identification or refugee registration documents can fully access onboarding and career guidance through a verified `no_documents` or partner referral route.
3. **Strict Domain Segregation**: Sensitive accommodation preferences and support notes are kept in a walled-off database store. Public job applications never expose medical or support requests unless explicit affirmative consent is granted.
4. **Zero URL Secrets**: Session recovery links sent via SMS or email contain opaque, single-use tokens; database records store only salted SHA-256 hashes of these tokens.

## 2. Cryptographic Architecture (AES-256-GCM)

Sensitive personally identifiable data (e.g. identity reference numbers, confidential accommodation notes) is encrypted using **authenticated symmetric encryption (AES-256-GCM)**.

### 2.1 Encryption Specifications
- **Algorithm**: `aes-256-gcm`
- **Key Derivation**: 256-bit key derived deterministically via SHA-256 from the master secret (`env.ENCRYPTION_KEY`).
- **Initialization Vector (IV)**: 12 bytes (96 bits) of cryptographically secure random bytes generated per encryption.
- **Authentication Tag**: 16 bytes (128 bits) generated by the GCM cipher. Guarantees message integrity and authenticity.
- **Key Versioning Format**: Serialized as `v1:<iv_hex>:<tag_hex>:<ciphertext_hex>`.
  - Enables seamless key rotation and multi-version key rings without database downtime.

### 2.2 Tampering Defense
Any alteration to the ciphertext or authentication tag causes a GCM authentication failure during decryption, rejecting the tampered payload.

## 3. Token Lifecycle & Rotation Defense

### 3.1 Access Tokens
- **Lifespan**: Short-lived (15 minutes).
- **Signing**: HMAC-SHA256 (`env.JWT_SECRET`).
- **Payload**: Minimal required claims (`sub`, `email`, `role`, `organizationId`).

### 3.2 Refresh Token Rotation with Token Reuse Detection
```
Client                      Server                      Database (RefreshTokens)
  |                           |                                    |
  |-- POST /auth/refresh ---->|                                    |
  |   (Token A)               |-- Find token by SHA-256 hash ----->|
  |                           |<-- Token A record (isRevoked?) ----|
  |                           |                                    |
  |                           | [IF isRevoked == true]             |
  |                           | Suspicious reuse detected!         |
  |                           |-- Revoke all in family ----------->|
  |                           |<- Return 403 Forbidden ------------|
  |                           |                                    |
  |                           | [IF isRevoked == false]            |
  |                           |-- Mark Token A isRevoked=true ---->|
  |                           |-- Issue Token B in same family --->|
  |<-- New Access + Token B --|                                    |
```

If an attacker intercepts a previously consumed refresh token and attempts to replay it, the server detects the reuse, flags the entire token family, and terminates all active sessions associated with that family.

## 4. Addendum D4: Employer Safeguards Enforcement

The backend enforces strict semantic validation on employer job descriptions, application requirements, and accommodation postings.

### Prohibited Patterns:
Any employer submission containing the following patterns is rejected with `400 VALIDATION_ERROR`:
- `\b(diagnosis|diagnoses|diagnosed)\b`
- `\b(medical\s+proof|medical\s+certificate|doctor'?s?\s+note|physician\s+letter)\b`
- `\b(disability\s+certificate|disability\s+card|disability\s+type|disability\s+category)\b`
- `\b(prove\s+your\s+disability|proof\s+of\s+disability|icd-?10|medical\s+records?)\b`
- `\b(state\s+your\s+condition|name\s+your\s+illness|disclose\s+your\s+disability)\b`

**Guidance returned to employers:**
> *"Do not ask applicants for medical proof or diagnosis. Describe the workplace adjustment or accommodation your team provides instead."*

## 5. Structured Log Redaction

Pino structured logging automatically redacts sensitive fields across HTTP requests and error logs:
- `req.headers.authorization`
- `req.headers["x-api-key"]`
- `password` / `passwordHash`
- `token` / `accessToken` / `refreshToken`
- `phone` / `phoneNumber`
- `identityDocument` / `nationalId`
- Plaintext censored value: `[REDACTED]`
